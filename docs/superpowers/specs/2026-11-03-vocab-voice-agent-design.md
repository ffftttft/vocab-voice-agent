# 个人定制化英语学习 Agent —— 设计文档

**日期**：2026-11-03
**状态**：已实施中（见 STATUS.md）
**实现计划**：`docs/superpowers/plans/`

---

## 1. 意图与缘由

用户是一名**程序员**，正在准备跳槽外企。当前英语水平的状态是他自己描述的：
「完全开不了口，或者说只会读一些简单的单词，但不会说句子，单词量也一般」。

他要的不是一个泛用的背单词软件，而是一个**能把「认识的词」变成「说得出的话」的闭环**。
这个区分是整个设计的地基：

- **识别**（看英文选中文）与**产出**（想表达 → 调出英文）走的是不同的检索通路。
- 一个人可以认出几千个词（用户就是这种情况），却依然组织不出一个句子。
- 因此本系统的价值重心在**语音产出环节**，背词环节是为它供弹药的。

用户明确要求：**系统全部实现完成后才开始使用**。所以他不在乎「第一周就能用」，
而在乎**建成后的完成度和可持续性**。

## 2. 目标 / 非目标 / 反目标

### 目标
1. 每天用 FSRS 高效维护词汇量，且词是**按场景成组学的**，不是 A-Z 顺序。
2. 例句是**用户现实中会说出口的话**（贴合程序员语境与当日场景），不是词典例句。
3. 每晚 10 分钟真实语音对话，逼用户把当天的词说出来。
4. AI 的纠错**不打断对话流**（Recast 技巧），只在屏幕上轻提示。
5. 卡壳时能主动求援（SSE 实时示例回答），用完即弃，不预生成。
6. 模型全部可热切换，换厂商不改代码。
7. 次日自动沉淀记忆（个人画像 + 语言病历），清空冗长上下文。

### 非目标
- 不做注册登录、不做多租户（MVP 单用户）。
- 不做课后影子跟读 / 复盘模块（SPEC 已明确排除）。
- 不做移动端原生 App（只做 H5/PWA）。
- 不做社交、排行榜、打卡激励。

### 反目标（技术上成功但产品上失败）
- **背词变成了负担**：每日 30 新词对「开不了口」的人是劝退而非训练。
- **语音通话变成单向演讲**：AI 说得多，用户说得少。
- **纠错变成打断**：用户正说到兴头上被纠正发音，体验崩塌。
- **提示按钮变成拐杖**：用户每句都点提示，等于抄答案。
  → 因此 `hint_requested` 被记录，用于区分「无提示主动掌握」和「看提示才用出」。
- **例句像鸡汤**：脱离用户真实语境的例句无法迁移到实际对话。

## 3. 约束

| 类型 | 约束 |
|---|---|
| 平台 | 单台云服务器；移动端 H5 优先 |
| 浏览器 | 手机浏览器要求 HTTPS 才给麦克风权限 → 必须有域名 + Caddy 自动证书 |
| 语言 | Python 3.12+ 后端；React 19 + TS 前端 |
| 包管理 | uv，PEP 735 `dependency-groups` 区分 dev/prod |
| 数据库 | SQLite（单机）+ WAL（并发读写） |
| 算法 | py-fsrs >= 6.3.2 |
| 并发模型 | 单进程异步 Event Loop（内存中的语音会话状态） |
| 成本 | 文本模型走中转站；语音模型走官方（延迟与音质优先） |
| 用户输入 | 词书暂无 → M2 用测试词跑通 |

## 4. 架构

### 4.1 分层

```
┌─────────────────────────────────────────────┐
│  web/  React H5（4 个视图 + Web Audio）       │
└──────────────┬──────────────────────────────┘
               │ REST / SSE / WebSocket
┌──────────────┴──────────────────────────────┐
│  api/   FastAPI 路由层（薄）                  │
├─────────────────────────────────────────────┤
│  harness/   业务编排（确定性，非黑盒框架）      │
│    daily_planner / voice_orchestrator        │
│    hint_streamer / memory_compactor          │
├─────────────────────────────────────────────┤
│  services/  FSRS / 记忆 / 词书                │
├─────────────────────────────────────────────┤
│  providers/  三大抽象接口 + registry          │
├─────────────────────────────────────────────┤
│  db/  SQLAlchemy Async + SQLite WAL          │
└─────────────────────────────────────────────┘
```

### 4.2 为什么自研 Harness 而不用 LangChain

SPEC 的硬性要求，且理由成立：本系统的「智能」集中在**三个确定性编排**上
（滑动窗口注入、Tool 拦截、记忆归并），用重框架反而增加不可控性。
自研部分预计 < 300 行，且每一行都可断点调试。

### 4.3 Provider 抽象（核心铁律）

业务代码只依赖 `providers/base.py` 的三个抽象类。具体实现的映射集中在
`providers/registry.py`，新增厂商只需登记一行。

**可验证的约束**：`src/agent_server/harness/` 与 `services/` 中
不允许出现 `import openai` / `import edge_tts` / 任何具体厂商名。

## 5. 数据模型

七张表，见 `src/agent_server/db/models.py`：

`words` / `fsrs_cards` / `daily_study_plans` / `daily_plan_items` /
`voice_sessions` / `linguistic_mistakes` / `daily_plan_items.hint_requested`

### 与 SPEC 的偏差（重要）

| 编号 | SPEC 写的 | 实际做法 | 原因 |
|---|---|---|---|
| **D1** | `state = 0` 表示 New，用 `WHERE state == 0` 查新词 | 用 `stability IS NULL` 判定新卡 | 实测 py-fsrs 6.3.2 的 `State` 只有 `Learning(1)/Review(2)/Relearning(3)`，**不存在 0**。照抄会导致每日新词恒为 0 |
| **D2** | `fsrs_cards` 有 `reps` / `lapses` 并期望与 py-fsrs 同步 | ORM 侧自行累加，仅用于统计 | py-fsrs 的 `Card` 对象没有这两个字段，`to_dict()` 也不含它们 |
| **D6** | 无 `user_id` | 所有业务表带 `user_id`，MVP 恒为 `local-user` | 用户提到「后期可能商业化」。加一列成本≈0，事后迁移成本极高 |

**D1 的证据**（可复现）：

```python
>>> from fsrs import State, Card
>>> [s.name for s in State]
['Learning', 'Review', 'Relearning']
>>> c = Card()
>>> c.state, c.step, c.stability
(<State.Learning: 1>, 0, None)
```

## 6. 难度参数（D3-D5）

用户自述「完全开不了口」，而 SPEC 的参数是按「有基础、缺练习」设计的。
若照抄，第一周就会因为挫败感而弃用 —— 这直接违背「天天要用」这个验收标准。

| 参数 | SPEC | 本设计 | 上调时机 |
|---|---|---|---|
| 每日新词 | 30 | **15** | 连续 7 天完成率 > 90% 且自评「太简单」比例 > 30% |
| 语音目标词 | 22 | **12** | 同上 |
| 通话时长 | 20-30 min | **10 min** | 连续 5 天说完 10 分钟无疲劳 |
| 复习上限 | 90 | 90（保留） | — |

**这些值在 `config.yaml` 里，改数字即可，不需要改代码。**

### 为什么不做「中→英」产出练习（用户已决定）

我提出过在背词环节加一步产出练习来补「识别 vs 产出」缺口。用户选择
**「先放缓节奏，不加新模态」**：先把节奏降下来建立开口惯性，跑一周看真实感受再调。
这个决定是对的 —— 在没验证过真实承受度之前加复杂度，是在猜测上盖楼。

替代方案：**提示按钮从「卡壳时的辅助」升格为「主学习路径」**。
用户前两周频繁点提示是预期行为，不是失败信号。

## 7. 关键机制

### 7.1 每日组局（daily_planner）

```
取到期复习词(≤90)
   ↓
统计这些词的 topic_tags 频次 → 得当日主场景
   ↓
从新词池筛出该场景候选(~80) → LLM 选 15 个并拟场景标题
   ↓
按批(15/批)并发：生成定制例句 + 同词性 4 选 1
   ↓
异步预热 TTS 音频
```

**Prompt 硬约束**（写在 `daily_planner` 里）：
- 例句 10~22 词，必须符合 `user_profile.md` 与当日场景
- 4 个选项**词性完全一致**
- 3 个干扰项：1 形近词 + 1 反义/近义边界 + 1 同场景常见词

### 7.2 滑动窗口目标词注入

不把 12 个目标词全塞进 system prompt（会失焦）。维护容量 4 的活跃窗口，
每次只注入当前 4 个词及其当日例句。模型调 `mark_word_used` 移出，
补下一个，通过 `update_instructions()` 静默刷新。

### 7.3 纠错双轨制

- **轻微错误** → Recast（用正确形式重述用户意思）+ 静默 `log_mistake`
  + 前端顶部非阻断卡片（5 秒后收进错题盒）
- **明显发音错误** → 温和插一句口头纠正 + 慢速示范一次，让用户跟读

**铁律：不打断对话流。** 这是产品体验的红线，不是优化项。

### 7.4 按需 SSE 提示

**绝不预生成。** 只在用户点按钮时才请求，流式返回 `EN:` / `ZH:` 两行。
同时把当前活跃窗口的词标记 `hint_requested = True`，防止后续照念被误判为主动掌握。

### 7.5 记忆压缩

次日凌晨（或点「结束今日学习」时）：
```
今日 transcript + 今日 mistakes + 现有两份 md
   ↓  LLM 结构化归并
user_profile.md 的「## 近期动态」追加新事实
error_patterns.md 按发音/语法聚合，保留 Top 15
   ↓
transcript_json 置 NULL（释放空间 + 隔离上下文）
```

**实现约束**：`MemoryStore` 只做追加/裁剪，不整体重写 —— 因为文件是用户可手改的。

## 8. 实现路线（已选）

**垂直切片**，而非 SPEC 的严格 M1→M5 顺序。

| 切片 | 内容 | 独立验收标准 |
|---|---|---|
| S1 | 脚手架 + DB + FSRS + 词书导入 + 最小背词页 | 能真刷词、有发音 |
| S2 | AI 智能组局（例句/4选1/场景聚类） | 例句贴合画像与场景 |
| S3 | 语音最小闭环 + 真机音频链路验证 | 手机能对着说话并听到回复 |
| S4 | 滑动窗口 / Tool 纠错 / SSE 提示 / 记忆压缩 | 完整闭环 |
| S5 | Docker 打包 + Caddy | 一键构建，服务能起 |

**为什么切片而非按 spec 顺序**：用户要求全部完成才用，所以「尽早可用」不是目的；
但**最大技术风险（实时语音）要被尽早暴露**，否则返工成本会在厚代码上叠加。

## 9. 留给实现者的决定

以下几点我有意不规定，实现时可自行判断：
- 前端组件库的具体选型（Tailwind 之外是否需要 headless UI）
- 音频 Worklet 的重采样算法细节（线性插值足够，不要求 polyphase）
- `daily_planner` 的批大小（15 是起点，可按实际延迟调整）
- 词书标签初始化的调度方式（后台任务 or 导入时同步）

## 10. 已知的取舍与代价

1. **单进程限制**：语音会话状态在内存，无法水平扩展。对自用场景可接受。
2. **SQLite 上限**：单机够用，但将来真商业化必须迁 Postgres。
3. **Edge-TTS 依赖微软非公开接口**：可能随时失效，因此 TTS 是 Provider 抽象，
   换商业 TTS 只需加一个实现类。
4. **`user_id` 预留**：如果最终不做商业化，这几个列是纯冗余（成本接近 0）。
5. **豆包适配器未实现**：SPEC 列为备选，但无 key 无法验收，MVP 不写空壳。
